# Seasonal AI Activities Design

## Goal

Activity suggestions should be concrete destination recommendations, not generic prompts such as "try local cuisine" or "look for a club." For any destination in the app, the activity flow should reuse fresh AI-discovered activities already stored in Supabase before calling AI again.

## Current Behavior

The mobile activity path calls the `activities-search` Supabase Edge Function, which searches Overpass and uses fallback activities when it does not have enough concrete results. The mobile completion layer then pads selected interest categories with additional fallback seeds. Food, nightlife, and shopping interests can therefore produce generic cards even though the feature is expected to find actual places and experiences.

`trip_activities` currently stores per-trip activity rows. That table is the right place for trip selection state and packing-list relationships, but it is not a reusable catalog for other users or future trips.

## Recommended Architecture

Add a shared seasonal activity catalog in Supabase. The catalog stores reusable activity discoveries for any destination and any supported interest set. Returned catalog rows are copied into `trip_activities` for each trip so users can select activities without changing the shared catalog.

The activity Edge Function becomes the decision point:

1. Normalize the trip destination and determine the season for the trip dates.
2. Query the shared catalog for fresh activities that match the destination, season, and requested interests.
3. Return fresh catalog activities when coverage is sufficient.
4. When coverage is missing or stale, call AI to generate concrete named places or specific destination experiences for the missing interest areas.
5. Validate and store accepted AI activities in the shared catalog with freshness metadata.
6. Return concrete results to the mobile app, which persists per-trip copies in `trip_activities`.

Overpass can still supplement the returned set when it provides named places. It should not be used to justify generic client-side filler for selected food, nightlife, shopping, or other interests.

## Shared Catalog Data

The shared Supabase table should represent reusable recommendations, not trip selections. A row should include:

- Stable row id.
- Normalized destination key.
- Display destination name.
- Country code and destination coordinates when available.
- Season bucket: `spring`, `summer`, `fall`, or `winter`.
- Activity name.
- Activity type.
- Interest tags that explain which user interests the row satisfies.
- Description.
- Source metadata, including AI source and generation version.
- Optional external place id or source reference if a concrete provider supplies one.
- Creation timestamp.
- Freshness timestamp such as `expires_at` or `refresh_after`.

Destination matching must work for any app destination, not a hardcoded city list. It should prefer stable identity inputs already available from trip destination selection, such as normalized destination text plus country and coordinates, so similarly named places do not collide unnecessarily.

## Seasonal Refresh

The cache should be seasonal rather than tied to an exact trip date range. A trip is mapped to a season bucket based on its activity date context. Fresh rows in the matching destination-season bucket can be reused for later trips until their freshness timestamp passes.

The first implementation should use a TTL near one season, such as 90 to 120 days, and include a generation version in matching logic. Changing the generation contract or prompt should invalidate older generated rows without requiring destructive cleanup.

Expired rows do not need to disappear immediately. They can be ignored during lookup and replaced by fresh AI-generated rows on demand. A cleanup job can be added later if table growth requires it.

## Interest Matching

The catalog should store individual activities tagged by supported app interests. A trip requesting `nightclubs`, `museums`, and `street_food` can reuse matching fresh rows from a destination-season catalog even if those rows were generated by earlier trips with partially overlapping interests.

Coverage should be evaluated by requested interest area, not only by total row count. If the catalog has many museum rows but no nightlife rows, AI should fill the missing nightlife coverage rather than returning a generic nightlife card.

## AI Generation Contract

AI-generated activities must be concrete:

- Prefer actual named places, venues, restaurants, markets, tours, landmarks, or destination-specific experiences.
- Include interest tags and activity types that match the app taxonomy.
- Avoid generic instructions, placeholder categories, and "look for" phrasing.
- Return structured JSON that the Edge Function validates before storage.

The generator should request missing destination-season-interest coverage and return enough choices for the trip without filling the list with low-specificity rows.

## Mobile Behavior

The mobile app keeps fetching activity suggestions through Supabase and keeps storing returned suggestions in `trip_activities`. Existing activity selection and packing-list behavior stay per-trip.

Generic completion seeds for named-place interests should be removed from the success path. If the shared catalog and generation path cannot produce concrete results, the app should show fewer concrete activities or a retry/error state instead of presenting generic filler as a suggestion.

## Failure Handling

- If the catalog has sufficient fresh rows, AI provider failure does not affect the trip.
- If AI fails while filling missing coverage, return any concrete catalog or provider rows already available.
- Do not persist invalid AI rows or generic placeholders into the shared catalog.
- Keep service-role-only write access for shared generated activity storage through Edge Functions.

## Testing

Implementation should cover:

- Season bucketing for trip dates.
- Destination and interest lookup behavior for shared catalog rows.
- Cache hit behavior that skips AI generation.
- Cache miss or stale-row behavior that invokes AI and stores validated rows.
- Missing-coverage behavior for partially populated interest sets.
- Rejection of generic or malformed AI rows.
- Mobile behavior that no longer pads concrete-interest results with generic nightlife, dining, or shopping cards.

## Out Of Scope

- A full editorial moderation workflow for AI activity rows.
- Exact event ticket availability or live opening-hours validation.
- Personalized ranking beyond destination, season, and requested interests.
- Immediate deletion of expired generated rows.
